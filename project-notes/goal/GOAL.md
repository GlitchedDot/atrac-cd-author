# Native Mac app that makes ATRAC3+ CDs for the D-NE1

Goal ID: goal_e35963ec4aae
Goal slug: native-mac-app-that-makes-atrac3-cds-for-the-d-ne1
Set by Lola 2026-10-21: "All I want is a native Mac app that makes Atrac3+ CDs for my NE1."
Delivery re-scoped by Lola 2026-10-22: BOTH — a web app first, and a native app too, "cuz not everyone wants to use the web browser."

## Description
Lola wants SonicStage's one essential job — burning ATRAC3+ CDs for her Sony D-NE1 Walkman — as a native Mac app, with no Windows machine and no SonicStage involved. The disc layout and the ATRAC3+ encoder are the reverse-engineering work; her own SonicStage-burned discs and the D-NE1 itself are the ground truth and the judge.

## Scope (exactly this, nothing more)

- ONE job, TWO delivery shapes (Lola, 2026-10-22, superseding the native-only framing): authoring ATRAC3+ CDs that her Sony D-NE1 ATRAC CD Walkman plays. FIRST a WEB app — the pipeline core compiled to WebAssembly, running in the browser on any of her machines, outputting a finished ISO the user burns in Finder (browsers cannot drive a burner: WebUSB blocks storage-class devices, no web API for burning). ALSO a NATIVE Mac app (her Macs are Intel; daily driver is the 2014 MacBook Pro on OCLP Tahoe) wrapping the same core with direct burning — because not everyone wants to use the web browser (her words). The pipeline core (decode -> encode -> encrypt -> author) is shared; only the shells differ.
- NOT a SonicStage clone, NOT library management, NOT NetMD, NOT a converter suite. One job.
- **The point of the whole project, in Lola's words (2026-10-22): "I don't mind dealing with an ISO, I just don't want to do the whole converting mumbo jumbo anymore. Just want it done all in one place."** Handling the finished ISO (and burning it in Finder) is explicitly fine with her; the enemy is the multi-tool conversion chain (tag cleanup -> fre:ac -> staged folders -> SonicStage import). One place, drop to done — that is the design center both shells are judged against.
- **Tag handling — the Kid3 step, built in (Lola, 2026-10-22): the app normalizes tags itself; ID3 tags MUST work.** Her rules, exactly: (1) if a file carries ID3v2.x tags, copy them into the ID3v1 field set and the v2 tags are completely removed from what the pipeline uses; (2) if a file has no tags at all, the filename becomes the ID3v1 title (track name) at minimum. The normalized fields are her ID3v1.1 set — Title / Artist / Album (+ track number) — and they feed BOTH disc outputs the way SonicStage's do: the .ATP's own ID3 tag and the NDB "ARTIST - TITLE" strings. Normalization is internal to the pipeline by default, and source files are NEVER silently rewritten: writing the cleaned tags back to the original files is an explicit user OPTION (off by default) — settled by Lola 2026-10-22, because not everyone would want that to happen automatically. UI: a checkbox/switch (per shell) that reveals editable fields for the currently selected track, so she can fix or fill tags by hand; with it off, the automatic rules just run. UI details are fine-tune-later, per her words; the behavior above is the spec. Note the v1 field limit (30 chars for title/artist/album) applies when copying down from v2.
- **Direct conversion (Lola, 2026-10-21): the app itself converts other audio files** (MP3/WAV/FLAC/etc.) into what the disc needs — no separate convert-then-import steps for her. Pipeline: decode any input (ffmpeg) -> resample to 44.1 kHz/16-bit -> ATRAC3+ encode (atracdenc, selected rate) -> encrypt -> author. Source files' tags carry into the .ATP ID3 + NDB titles.
- **Absolute-max fill (Lola, 2026-10-22): the app targets the blank's exact capacity as a hard ceiling and can fill to it.** ATRAC CDs are data discs, so capacity is exact: sectors x 2,048 user bytes — an 80-minute blank = 360,000 sectors = 737,280,000 B (703.1 MiB); 74-minute = 681,984,000 B. **Blank size is chosen from a dropdown menu** (Lola, 2026-10-22 — she uses the small discs too and wants them supported later): 12 cm 80 min (737,280,000 B, the default), 12 cm 74 min (681,984,000 B), 8 cm pocket 24 min (221,184,000 B), 8 cm pocket 21 min (193,536,000 B), 12 cm 90 min overburn (829,440,000 B), 12 cm 99 min overburn (912,384,000 B), plus a Custom entry (type MB or sectors — covers business-card and other odd-shaped media, which vary too much to preset). The app budgets every byte against the chosen blank: each track costs its audio + exactly 1,120 B (measured: 1,024 B ID3 + 96 B secure header), plus the layout files and ISO structures, all computed, not estimated. It shows remaining space live as tracks are added, NEVER emits an over-capacity ISO, and offers a fill mode: for a small playlist, climb the bitrate ladder so the disc lands as close to the ceiling as possible without crossing it (this is the mechanism behind her earlier "fill more of the CD with smaller playlists" requirement). 90/99-minute overburn blanks exist but are a separate D-NE1 verdict question; 80-minute is the default target.
- **Playlists + GROUPS are MANDATORY (Lola, 2026-10-22).** Making a playlist (picking and ordering the tracks for the disc) is a required feature of both shells, not a later extra. On the disc, that playlist becomes a GROUP (GROUP.NDB records + per-track group assignment in TOC00000.STI): a group is basically a folder (Lola's words, as in SonicStage) — the D-NE1 navigates by group, and multi-album discs are organized as several groups on one disc. Format note from our own author evidence: both of her reference discs carry an EMPTY PLLIST.NDB and an empty playlist STI — whatever SonicStage's UI calls it, the organization the disc actually carries is groups. Every track on a disc must belong to a group (the author's group-coverage check enforces this; an uncovered track is an error, never a silent orphan).
- **GUI direction (Lola, 2026-10-21): make the app's GUI similar to the original SonicStage** — its layout language (source/track panes, disc view with groups and track order, the transfer/burn flow) and its purple-era look, rebuilt natively in each shell (web UI for the web app, native Mac controls for the Mac app). **Web shell specified tighter by Lola (2026-10-22): the web UI won't change much — it just looks like the burning page from SonicStage** (the ATRAC CD creation view: track list, disc contents with capacity, the burn flow). The features she specced live naturally on that page: the blank-size dropdown, the remaining-space/fill readout, the tag-editor checkbox. Look-alike, not asset-ripped: Sony's bitmaps/code stay Sony's; the arrangement and feel are the target. Applies at the app-shell stage, after the pipeline works.
- If this lands, it retires the premise of the headless SonicStage PC and the Windows dependency for her ATRAC CD workflow — her call, noted not decided.

## The two technical unknowns (stage-0 settles both)

1. **Disc layout**: the exact file/control structure SonicStage writes on an ATRAC3+ CD that the D-NE1 firmware expects. Ground truth available: her own SonicStage-burned discs (read one sector by sector) + SonicStage's writer components in Ghidra. Bounded, feasible RE.
2. **ATRAC3+ ENCODER — was the crux, now a test question.** CORRECTED 2026-10-21 (the filing text claimed no open ATRAC3+ encoder exists — wrong, verified against the primary source): **atracdenc** (github.com/dcherednik/atracdenc, LGPL-2.1) documents ATRAC3PLUS encoding to OMA/RIFF/RAW (`./atracdenc -e atrac3plus -i in.wav -o out.oma`); its only input limit is 44.1 kHz 16-bit WAV, which matches CD rips exactly. Full brief: `files/stage0-encoder-brief.md`. What remains genuinely open: (a) the ATRAC3plus path's maturity/quality (community coverage is thin — MiniDisc barely uses it), and (b) whether the D-NE1 firmware accepts atracdenc-encoded streams on an authored disc. Both are settled by ONE test encode + ONE test disc, not by writing an encoder. Only if the D-NE1 rejects atracdenc streams does "write an encoder" become the long pole again. Fallbacks unchanged: author from ATRAC3+ files she already has (no encoder needed); ATRAC3-instead-of-3+ is hers to accept or reject, never assumed.

(2) Disc readout — DONE (NDB records cracked: 256 B header + 128 B fixed records, UTF-16BE titles; audio is OpenMG-encrypted at the burn step; library files are clean). (3) Evidence collection — DONE 2026-10-21: full Toshiba install + entire Sony Shared tree in hand (readouts #1-#5 in files/).
- **Stage 0.5 (analysis, next; Candy's desk work)**: Ghidra on CDRFormatter.dll (layout writer: STI field semantics, filesystem specifics), omgatpcd.dll + OpcKdr.dll + the shipped .ekb files (THE GATE: the disc encryption and how 0001000E.STK's key block is produced — if this can't be reproduced, the app dies here, so it goes first), OpcAtp/AtpFringe (the .ATP wrapper + plaintext header). Parallel workstream: extend atracdenc with real bitrate support (64 kbps first, then the ladder).
- **Test discs (the verdicts)**: Disc A — a known-good Sony-encoded library track re-wrapped with OUR layout+encryption: judges layout/crypto alone. Disc B — an atracdenc-encoded track: judges the encoder. Two discs, two separate questions. Lola burns + plays; her D-NE1 and ears are the verdict.
- **Stage 1**: full test discs (her tracks, her bitrates); Lola burns and plays them in the D-NE1. Her ears/screen are the verdict (never declare playable from files alone).
- **Stage 2a**: the WEB app wrapping the pipeline core (compiled to WebAssembly): pick files -> encode (atracdenc) -> encrypt -> author -> download the finished ISO; the user burns it in Finder. GUI per Lola's direction: SonicStage-like layout and look in web UI. HOSTING (Lola, 2026-10-22): her GitHub — a static repo + GitHub Pages (free on a public repo; the app is fully client-side, no server component; contains no Sony assets — users bring their own audio). Design constraint from Pages: no custom response headers, so no SharedArrayBuffer — WASM builds must be single-threaded (encoder and decoder cores both have single-thread builds; fine).
- **Stage 2b**: the NATIVE Mac app wrapping the same core: pick files -> encode -> author -> burn directly (macOS DiscRecording/drutil).
- **Stage 3 — LAST, parked until the core works and is stable (Lola, 2026-10-22)**: Windows and Linux versions. Her priority order is explicit: get it working first, and stably — these come after. The shared pipeline core is platform-neutral by design, so they are new shells around the same engine, not new engines; noted here so the roadmap holds them, and not started early. GUI per Lola's direction: SonicStage-like layout and look on native controls. Reference screenshots of her SonicStage (main window + ATRAC CD creation view) would pin the target — requested 2026-10-21, optional, not blocking.
