### salexec is a working door, and atpcd's Encrypt was entered

- The "poi poi poi" wall fell in run 105: salexec returned cleanly for the first time in the harness's history (EAX=0, out buffer `01 00`, non-zero for the first time), and run 106 reproduced it byte-identically after a genuine harness code edit. The spec's trailing block is a plaintext S-expression of counted atoms, not the binary SalAsn format previously assumed; `"{p001}"` is a well-formed spec.
- The gate was simpler than the parser theory: salexec compares the name passed against the loaded SAL file's entry table and throws "poi poi poi" when there is no match. `init.ocm` (582 KB) is only an init shell; the real init file is `init2.ocm` (8.5 KB), whose entry 0 is named GetVersion.
- Two brief misreadings were caught by the sessions with evidence and must not be reused: "GetImplementationCount" exists nowhere in the binaries (the address given for it was mid-function), and `FUN_65101730` is a C++ string copy constructor, not a loader. Brief addresses and names are to be verified against the binaries before delegating — this is now an explicit discipline, after two catches in a row.
- The real module pipeline was mapped end to end: modules are fetched whole (`FUN_6511b160` — cache lookup, file read, no envelope parsing anywhere) and then executed or referenced inside the SAL VM by reference, as (length, pointer) pairs in small binary records. The earlier checksum/envelope mysteries evaporate under this model; there was never a gate to pass there. The device.sal-only registrar that threw "device.sal verify failed" for atpcd.ocm was a category error, not a CRC failure: .ocm envelopes carry a format constant (`0x2c10`) where device.sal keeps a genuine self-checksum, and device.sal's own checksum was replicated exactly outside the engine (`0x4bbbc796` == stored).
- atpcd.ocm fetches cleanly, byte-identical to the corpus copy. In run 111, transplanting atpcd's reference into region.ocm's invocation record dispatched into atpcd's routine named "Encrypt" and entered it; the engine rejected it with `ERR_TYPE`, an argument-type error, because it was handed region's arguments. The project is therefore no longer looking for the Encrypt door; it is standing inside the routine with the wrong paperwork.
- Session 9 reframed the method: instead of guessing record shapes, it decompiled the actual driver, `omgatpcd.dll`, the SonicStage component that talks to the SAL layer. Requests are typed streams built with writer calls (octet strings, buffer references, ints, module references) and executed through the manager. The hand-rolled transplant records were close enough to be accepted but semantically inert — run 121 proved the VM just echoes such arguments back verbatim, never transforms them.

### The pfcom MAC: localized to the IntegrityCheckID GUID, then to a second per-run input

- The "bad ProcessFile MAC" is not a comparison in pfcom at all. The whole verify is computed inside maclist.ocm: salwrap feeds it the .opf's first key plus a 100-byte install record, and maclist returns a status — 2 means "bad MAC," which salwrap translates into the throw. The inputs are everything.
- A housekeeping catch from that session: the harness had quietly invented its own install identity (self-generated ID files in its scratch folder). Those were replaced with Lola's genuine corpus files, MD5-verified, synthetics backed up. Necessary, but not sufficient.
- The one divergent input first identified was the install record's computed fields, keyed by the install's IntegrityCheckID GUID — proven by experiment, since seeding a GUID into the harness registry changed the record's fields deterministically. That GUID is in no file in the corpus; it lives in the Windows registry of the machine whose OpenMG install produced the corpus files.
- Recovery was already on disk: Lola sent the Toshiba's full registry export on 2026-10-21 (the 233 MB EKB-hunt export), and the value sits in it at `HKLM\SOFTWARE\Wow6432Node\Sony Corporation\OpenMG`, IntegrityCheckID = `{B34A50CC-E17B-ce5e-4445-D84F8778899C}` (exactly as stored, mixed case). Lola then confirmed it live on the Toshiba itself by screenshot, character for character identical to the export. The chain is airtight: install to export to harness seed, no guesswork.
- Session 12 was a partial falsification: the GUID went in, the engine consumed it, and op 4 still returned status 2 across three runs, no session. The GUID was necessary but is not the whole seal. The install record exists in two generations — a baseline form the engine persists to files and reloads next run (lagging one run behind), and a fresh form the ProcessFile constructor builds during session creation — and the fresh form's sealed fields change every single run even with registry, identity files, record lineage, and memory layout held frozen, and even with the OP-A replay removed entirely. A second per-run input feeds the seal. Named suspects, in order: wall-clock time (the harness's time functions return real time, and the engine demonstrably reads the clock), VM history (the harness runs test salexec calls before the probe; a real session-create process would not have that history, and this VM is stateful), or a random draw inside the constructor window. The specced diagnostic is: hook every write to the constructor's record buffer and log which code writes the sealed bytes and from what inputs, watch the clock calls in that window, and try a minimal run skipping the preliminary test calls. Do not treat the GUID as the solved MAC, and do not forge past the check — a bypassed MAC would poison every verification after it.
