## Session 28 (2026-10-30, runs 167–170) — the generation rule, and a live session

- The maclist pair lives in generations, and the byte diff across them is total and tiny: `maclist.dat` never changes; not one payload byte of `maclist1.dat` ever changes. Form-2 is the pristine 21,420-byte file plus a 20-byte trailer (dwords {6, 0, 7, 4} plus a big-endian generation counter = 1); form-3 differs from form-2 in exactly one byte (counter 1 → 2). `icv.dat` (20 bytes) is wholly rewrapped per pass.
- **The verify rule, named exactly:** FUN_65108840 returns true if and only if the seed handed to it is the value the pair's own extraction derives from the pair image **one generation before** the pair's current stamped generation. Evidence grid: run 164 TRUE (extract form-2 → write form-3 → verify in-process); runs 166/167 FALSE (form-1 pair with form-1's own seed, zero stale); run 169 FALSE (form-3 pair with form-1 seed, two stale); run 170 TRUE (form-2 pair with form-1 seed, one stale — a pre-registered prediction, confirmed).
- This also explains Lola's real install with no cold-start paradox: the pairing is established once, in some first-run era, and thereafter PACSPTISVR — the always-on service — simply holds the seed mapping open. Every later launch finds the seed already resident and takes the trust path.
- **Run 170 endpoint:** with the pairing satisfied, the verify passed, op 4 passed, invoke #5 passed, the init state (+0xbc) reached 2 for the first time, and the factory handed back a **live pfcom session object** (vtable matching the one on record, carrying `querycif.ocm` at +0x18). ## Session 30 (2026-10-30, runs 173–175) — the standalone door refuses by design; the real door is the typed stream

- Executing atpcd.ocm standalone through the bootstrap's SAL VM invoker (FUN_6512c840 parameter-block route) refuses in both VMs with exception (0x2), `ERR_TID_MTDD`. Session 30's framing was that modules split into plaintext programs and an encrypted library; Session 31 corrected part of that framing (see below), so do not reuse the word "plaintext" for any module body.
- What stands from Session 30: the invoker route runs program-type modules and refuses library-type atpcd.ocm (header `03 02 00 00`); atpcd's real execution door is the host **typed stream with an integer selector first**. The control experiment proved the library is alive — OP-A re-ran clean in run 174, and while it ran the VM fetched atpcd.ocm by name and issued an internal invoke inside it. Known integer selectors 0/1/2 are OP-A / BIND / media-info only.
- The session's mystery vt+0x68 slot was pinned as a call into querycif.ocm **op 11** (int 0x0b), embedding the op-3 content key, the caller buffer, and the content ID. In the reproduced session state it threw the same MTDD refusal, and pre-fetching / registering atpcd.ocm did **not** fix it (run 175 refuted) — which Session 30 read as op 11 linking some other library module.

## Session 31 (2026-10-31, run 176) — two doors closed with proof, one premise corrected

Lola authorised one more run overnight on 2026-10-31 at about 00:08 PDT ("do one more run while I sleep"); the morning report was delivered in main chat at 00:18 PDT. No ciphertext, but:

- **Correction to Session 30's premise:** no .ocm body is plaintext at rest. **All** .ocm bodies are encrypted at rest; the class-01 vs class-02 distinction is program-vs-library **type**, not plaintext-vs-encrypted. Even while executing, a program-type module never exists in memory as a readable stream — it runs as a web of linked frames and values. This matches the project's own earliest findings; Session 30's summary garbled it and the garble was carried into Session 31's brief, where the verify-first discipline caught it. Do not describe querycif (or any module) as a plaintext program in future briefs.
- **Op 11's refusal is a judgement, not a missing link:** its full error text names `ERR_MALFORMED_INPUT` (kind 0x14402020), raised **inside** querycif. Op 11 is not complaining about an unregistered module; it is judging the input it was handed and finding it malformed.
- **The burn-side caller is proven absent from all delivered material:** omgatpcd.dll is a pure COM server, and nothing in the three delivered corpora ever creates it except a registration checker. The CD-writing host that would call the transform was never delivered, so the transform's grammar cannot be reconstructed from a caller that does not exist here.
- **The remaining unknown is exactly op 11's input contract.** Op 11 receives the buffer, the key, and the content ID exactly as the real code builds them, so suspicion falls on the state behind them — some field derived from the track's `.opf` (ProcessFile state) that op 11 validates.
